# Go (layout oficial de módulos)

> Comece com poucos arquivos na raiz; use `internal/` para o que não é API pública e `cmd/` quando houver mais de um programa.

## O que é

A página oficial "Organizing a Go module" descreve sete formatos: pacote básico, comando básico, pacote ou comando com pacotes de apoio (`internal/`), vários pacotes, vários comandos, pacotes e comandos no mesmo repositório (`cmd/`) e projeto de servidor. Em todos, `go.mod` fica na raiz, e o nome do pacote segue o último trecho do caminho do módulo.

Para servidores, a recomendação é manter a lógica em `internal/` e os programas em `cmd/`, ao lado de pastas não Go (front, deploy, scripts). A página recomenda `internal/` para pacotes que você não quer expor como API; outros módulos não podem importar o que está em `internal/`, então você pode refatorá-los sem quebrar usuários externos. Só ajuste `cmd/` quando houver mais de um comando ou mistura de comandos com pacotes importáveis.

Sobre o repositório "golang-standards/project-layout": ele é popular, mas não é um padrão oficial do time do Go; o README do repositório diz que "NÃO é um padrão oficial definido pelo time do Go" e manda para a página go.dev acima (fonte: github.com/golang-standards/project-layout, README, conferido em 2026-11-24).

## Por que usar

- **Guia oficial por tipo de projeto:** sete formatos (go.dev/doc/modules/layout).
- **`internal/` não é importável por outros módulos** (go.dev/doc/modules/layout).
- **Começa na raiz:** o pacote básico tem todo o código na raiz do módulo e `internal/` entra quando for preciso dividir (mesma página).

## Quando usar

- Servidores (seção "Server project"), comandos ("Basic command") e pacotes importáveis ("Basic package"), todos em go.dev/doc/modules/layout.

## Quando é bom

- **Sem pasta obrigatória** além de `go.mod` na raiz (go.dev/doc/modules/layout).
- **Fronteira com `internal/`:** outros módulos não importam (mesma página).
- **Pacote por assunto:** o exemplo de servidor do guia usa `internal/auth`, `internal/metrics` e `internal/model`, próximo de [feature-first](01-feature-first-colocation.md).

## Quando é ruim

- **Tratar o golang-standards/project-layout como oficial:** o README dele diz que não é padrão oficial (github.com/golang-standards/project-layout).
- **Pacote `util`, `common` ou `misc`:** o blog do Go diz que esses nomes não dizem ao cliente o que o pacote oferece (go.dev/blog/package-names).
- **Tudo fora de `internal/`:** o que fica exportado precisa ser suportado; a página recomenda `internal/` para evitar isso (go.dev/doc/modules/layout).

## Como começar

Parte do layout "server project" da documentação: só o que go.dev/doc/modules/layout mostra (`go.mod`, `cmd/`, `internal/`). Os nomes dentro de `internal/` são exemplo.

```
meu-servico/
├── go.mod                          # OFICIAL: módulo, na raiz
├── cmd/                            # OFICIAL: um programa por pasta
│   └── api-server/
│       └── main.go                 # OFICIAL: comando em cmd/
└── internal/                       # OFICIAL: não importável por outros módulos
    └── auth/                       # OFICIAL: pacote em internal/ (internal/auth no guia)
        ├── auth.go
        └── auth_test.go            # teste ao lado, sufixo _test.go (go.dev/doc/tutorial/add-a-test)
```

Regras de nome e lugar:

- **Pacote:** minúsculas, sem `_` nem mixedCaps (go.dev/blog/package-names); nome de uma palavra (go.dev/doc/effective_go).
- **Teste:** arquivo `_test.go` (go.dev/doc/tutorial/add-a-test); fica na mesma pasta do código.
- **Servidor:** a lógica em `internal/` e os comandos em `cmd/` (go.dev/doc/modules/layout).
- **Projeto pequeno:** sem `cmd/`; o comando básico tem os arquivos `package main` na raiz (go.dev/doc/modules/layout).

## Combina com / alternativas

- [Feature-first](01-feature-first-colocation.md) e [monólito modular](04-monolito-modular.md): `internal/<modulo>`.
- [Camadas](03-camadas-clean-hexagonal.md): só quando o domínio pedir.
- O repositório golang-standards/project-layout diz no próprio README que não é um padrão oficial do time do Go e manda para go.dev/doc/modules/layout (conferido em 2026-11-24).

## Decisão rápida

- **Use se:** é back-end ou ferramenta em Go; siga a página oficial e use `internal/`.
- **Evite se:** a intenção é seguir o golang-standards/project-layout como se fosse oficial (o README diz que não é).
